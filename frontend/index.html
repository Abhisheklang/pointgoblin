PointGoblin is a real time planning poker application built to demonstrate a production style backend. FastAPI and WebSockets serve the rooms, Redis pub sub carries events between two API instances, PostgreSQL stores the record, and JWT auth separates hosts from guests. This page is the case study: architecture, engineering decisions, load test results, and a working live demo.

Overview

What was built and why

PointGoblin was built to demonstrate backend engineering on a small, complete system: a real time API, state shared across processes, a database record, authentication, and measured performance. Planning poker is the workload because it is genuinely real time. Every participant holds a live connection, votes arrive at unpredictable moments, and the reveal is a broadcast to the whole room at once.

The rule it implements is simple. Each person picks a story point card in secret, and no client can see any value until the host reveals. The server holds the vote values and never sends them before the reveal, so the rule holds in the protocol, not only on the screen. Hidden votes exist to stop anchoring, the pull that the first spoken number exerts on every later estimate.

  1. 01

    Rooms and guests

    Hosts register and sign in. Guests join a room with a six character code and a scoped token that works for that room only.

  2. 02

    Story queue

    The host adds stories to a queue and chooses which story is being voted on.

  3. 03

    Hidden voting

    The deck runs 0, 1, 2, 3, 5, 8, 13, 21, a question mark, and a pass card. The room shows who has voted and never what they picked.

  4. 04

    Reveal and record

    The host reveal computes the average and the agreement score on the server and writes the results to PostgreSQL.

  5. 05

    Presence

    Room membership lives in Redis with an expiry, separate from the stored record.

Live demo

The working application

The demo is the application itself, running against the API described on this page. It takes two browser windows to show the real time behaviour: one window as the host, one as a guest.

  1. 01

    Register and create a room

    Open the demo, register as a host, and create a room. Note the room code.

  2. 02

    Join as a guest

    In a second window, join with the room code and a display name. No account.

  3. 03

    The host adds a story and activates it. Both windows vote. Each window shows a card count and no values.

  4. 04

    The host reveals. Both windows flip every card at the same moment and show the average and the agreement score.

Architecture

Request and event flow
  1. 01

    Browser

    The React app calls REST endpoints for accounts and room setup, then holds one WebSocket connection per participant for live room state.

  2. 02

    API

    FastAPI routes call services, services call repositories, and repositories own the queries. Pydantic schemas validate every request and response.

  3. 03

    Database

    PostgreSQL, through SQLAlchemy, stores users, rooms, stories, and votes. Results are written at reveal time. WebSocket handlers use short lived sessions, so a connected client never holds a database connection.

  4. 04

    Event bus

    Every room event is published to Redis. Each API process keeps one shared subscription connection and fans messages out to its local sockets.

  5. 05

    Second instance

    A client connected to one instance receives events handled by another instance through Redis. The cross instance check in the loadtest folder proves this against two live processes.

Engineering decisions and trade offs

Scaling

Redis pub sub across instances

Keeping room events in process memory would cap the system at one API process. Publishing to Redis costs a network hop per event and buys horizontal scaling: any instance can serve any client.

Load

Broadcast coalescing

The first load test delivered 221,413 messages for 300 clients, because every join triggered a full state broadcast. Coalescing triggers inside a 75 ms window into one broadcast of the latest state cut delivery to 5,151 messages.

Correctness

Hidden state on the server

Before the reveal, room state contains voter names and a count, never values. Hiding values only in the interface would let any client read them from network traffic, so the withholding happens in the API itself.

Load test

Method and results

The load test script, in the loadtest folder of the repository, opens WebSocket clients against one room on one API process, measures connection time, times a single vote travelling to every client, then has every client vote at once and times full convergence. It ran on the development virtual machine used for this build, a small shared box, against local PostgreSQL and Redis.

Testing

What was verified
Backend

26 tests, all passing

Accounts and auth take 8 tests, room flow 7, voting rules and reveal maths 8, and a live WebSocket session with two clients in one room takes 3.

Static gates

Lint, format, types

Ruff and Black on the Python code, ESLint and Prettier on the frontend, and a strict TypeScript production build. All run in CI on every push.

Responsive

Four widths, zero overflow

Landing, demo entry, and room screens were checked at 360, 768, 1280, and 1920 pixels wide, with zero horizontal overflow and the full deck usable at 360.

Known limits

Stated plainly
  1. 01

    Docker Compose not run here

    The Compose file is written and validated, but Docker was not available in the build environment, so it was never run there. Every service in it was run and verified directly instead.

  2. 02

    Fonts load at runtime

    The display fonts load from a public font service when the page opens. Fallbacks are declared, and the layout holds without them.

  3. 03

    Trial configuration for media

    Screenshots and the recording were captured against SQLite with the in memory event bus. The PostgreSQL and Redis path was verified separately, with two API instances.

  4. 04

    No public deployment

    The project runs locally or under Compose. Nothing here is hosted, and the numbers on this page come from the local machine described in the load test section.

Tech stack

What it is built with
Backend

Python and FastAPI

FastAPI on Python 3.12, served by uvicorn. SQLAlchemy over PostgreSQL, Redis for pub sub and presence, PyJWT and bcrypt for auth, Pydantic for schemas.

Frontend

React and TypeScript

React with strict TypeScript, built by Vite and styled with Tailwind CSS and a small token based design system. This landing page is static HTML.

Infrastructure

Compose and CI

Docker Compose runs PostgreSQL, Redis, two API replicas, the frontend, and an nginx load balancer. Tests and lint run in GitHub Actions.

Run locally

Two ways

With Docker Compose, from the repository root:

cp .env.example .env  ·  docker compose up --build

Then open localhost:8080. Without Docker, run the backend with Python 3.11 or newer, PostgreSQL, and Redis:

cd backend  ·  uvicorn app.main:app --port 8000  ·  cd frontend  ·  npm run dev

Then open localhost:5173. Setting EVENT_BUS to memory runs everything inside one process, which is the configuration the test suite uses. Full instructions, including environment variables, are in the README of the repository.
